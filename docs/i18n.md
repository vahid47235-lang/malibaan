# Internationalization (i18n) architecture

Malibaan is bilingual: **Persian (fa, default)** at unprefixed URLs (`/about`,
`/services/accounting`) and **English (en)** under an `/en` prefix
(`/en/about`, `/en/services/accounting`). The two languages read as two
native sites, not a machine translation of one — copy, URLs, and metadata are
authored per language.

## How routing works

- `src/i18n/config.ts` — the single source of truth for supported locales
  (`locales`, `defaultLocale`, `localeMeta` for `dir`/`lang`/OG locale).
- `src/proxy.ts` — runs on every request. It:
  - Canonicalizes `/fa/...` → `/...` (308) so there's one indexable URL per page.
  - Passes `/en/...` straight through (it already matches the `[locale]` route).
  - For unprefixed paths: honors a saved `NEXT_LOCALE` cookie, or on a first
    visit, negotiates the browser's `Accept-Language` header; if that prefers
    a non-default locale, it 307-redirects to the prefixed URL. Otherwise it
    rewrites internally to `/fa/...` (URL stays unprefixed).
- All public routes live under `src/app/[locale]/...`, sharing one root
  layout (`src/app/[locale]/layout.tsx`) that sets `<html lang dir>` and the
  fonts. `/admin` and `/api` are intentionally outside `[locale]` — the admin
  panel is an internal, Persian-only tool and isn't part of the bilingual
  site.

## Translation content

- `src/locales/<locale>/*.json` — UI copy dictionaries, one JSON file per
  page/section namespace (`common`, `home`, `about`, `services`, `blog`,
  `calculator`, `contact`, `consultation`, `clients`, `legal`). Both locales'
  `index.ts` are typed against `src/i18n/dictionary-types.ts`, so a missing
  key in either language is a TypeScript build error, not a silent gap.
- `src/lib/data/*.fa.ts` / `*.en.ts` — long-form content that isn't simple
  key→string copy: services, blog posts, testimonials. Each has a shared
  index (`services.ts`, `blog.ts`, `testimonials.ts`) exposing
  locale-aware getters (`getServiceBySlug(locale, slug)`, etc).
- Blog posts carry a stable cross-locale `id` separate from their `slug`,
  because English slugs are written fresh (`private-joint-stock-vs-llc-...`),
  not transliterated from the Persian URL. A post may exist in only one
  locale — `getAvailableLocalesForPost(id)` drives hreflang/sitemap so a
  language that isn't published never gets linked.
- Pages call `getDictionary(locale)` (`src/i18n/get-dictionary.ts`, server-only)
  and pass the relevant slice down as props — components never fetch or guess
  their own locale.

## Links, switching, and formatting

- `src/components/i18n/link.tsx` — drop-in `next/link` replacement that
  auto-prefixes internal hrefs with the active locale (via
  `LocaleProvider`/`useLocale()` set once in the root layout). Use it instead
  of `next/link` in any component that renders an internal `<Link>`.
- `src/components/i18n/language-switcher.tsx` — the accessible language
  dropdown (keyboard nav, `role="menu"`), in the header (desktop + mobile).
- `src/i18n/format.ts` — `t()` for `{placeholder}` interpolation in dictionary
  strings, `formatNumber()`/`formatDate()` for locale-correct numerals and
  calendars (Persian digits + Jalali for fa, Gregorian for en).
- `src/i18n/seo.ts` — `buildAlternates()`/`ogLocaleFor()` for canonical +
  hreflang + OpenGraph locale metadata, used consistently across every page's
  `generateMetadata`.

## Adding a new language (e.g. Arabic)

1. Add `"ar"` to `locales` and an entry in `localeMeta` in `src/i18n/config.ts`
   (`dir: "rtl"`, `htmlLang: "ar"`, `ogLocale: "ar_SA"`, labels).
2. Add `src/locales/ar/*.json` mirroring the `en`/`fa` namespace files —
   TypeScript will flag any missing key against `dictionary-types.ts`.
3. Add `src/lib/data/services.ar.ts`, `blog.ar.ts`, `testimonials.ar.ts` (or
   leave content untranslated for a slower rollout — `getServices`/`getBlogPosts`
   etc. simply won't have Arabic entries until you add them; blog posts in
   particular are designed to support partial-locale coverage).
4. Nothing in `proxy.ts`, the routing tree, the language switcher, or any
   page needs to change — they all iterate over `locales`.

## Known scope limits (by design, not oversight)

- `/admin` stays Persian-only; it's an internal back-office tool.
- The fee calculator's service/category names and discount labels come from
  Postgres (managed via `/admin`), not from the translated data files. They
  render in Persian on both locales until the schema grows an `nameEn`
  column — everything around them (page copy, form labels, validation,
  currency suffix) is translated.
- The lead-capture popup (copy sourced from the DB, A/B tested from
  `/admin`) only renders on the Persian site for the same reason.
